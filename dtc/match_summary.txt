INFERRED COLUMN MAPPINGS  (DTC field  ->  ticket field)
  DTC order id:   dtc_row_id = 'DTC Row Id'; dtc_order_no = 'Invoice Id'
                  (DTC has no native ticket number of its own).
  Ticket row id:  matched_inbound_row_id / matched_outbound_row_id identify
                  exact source CSV lines, even when ticket numbers repeat
                  across several material lines.
  Material code:  DTC has NONE -> derived from 'Material Name' via a
                  description->code map built from the ticket files
                  (unambiguous: no description maps to two codes).
  Material desc:  DTC 'Material Name' -> inbound 'Material Name' / outbound 'Material'.
  Net weight:     DTC 'Yard Net Weight' (yard scale) -> ticket 'Net Weight';
                  fallback DTC 'Consumer Net Weight' (differs in 20/85 rows).
  Gross weight:   DTC has NO gross weight -> gross-weight component UNAVAILABLE
                  for every DTC pair (tickets carry gross, nothing to compare).
  Date:           DTC 'Invoice Issue Date' (fmt %m-%d-%y, %H:%M:%S, tz-naive)
                  -> outbound 'Date In' / inbound 'Effective Date' (ISO + IANA
                  zone, converted to tz-naive UTC). Possible intraday tz skew;
                  immaterial at the day-level windows used.
  Customer:       DTC 'Customer Name' = the BUYER -> outbound 'Customer Name' ONLY.
                  Inbound 'Customer Name' = SUPPLIER/vendor, NOT the DTC buyer ->
                  customer component UNAVAILABLE on the inbound side.
  Location/yard:  No DTC field maps to ticket yard ('Ship To *' is the consumer
                  destination) -> location component UNAVAILABLE (weight 0 used).
  Price/rate:     DTC 'Yard Value'/weight  ->  outbound 'Expected Value'/weight,
                  inbound 'Cost'/weight. Weak component.

EXCLUDED DETERMINISTIC KEYS (deliberately NOT used for matching)
  'Outbound Ticket Id' (85/85 -> outbound) and 'Sales Order #' (85/85 ->
  outbound 'Sales Order') would join DTC->outbound exactly, but the task is to
  INFER links from physical attributes, so both are excluded from scoring.
  'Outbound Ticket Id' is held out solely to report accuracy above.

DATE-WINDOW EVIDENCE (why the windows are tight)
  For direct-to-consumer flow, receipt/shipment/invoice cluster within days:
   - DTC invoice date vs true outbound date: within 3 days for 84/84.
   - DTC invoice date vs inbound effective date: -4..+3 days (median -1).

AUTOMATED INBOUND AGGREGATION & UNIQUENESS
  Aggregated inbound matches adopted: 15
  Distinct inbound source rows reused by assigned matches: 0
  Aggregation window: -30/+3 days;
  max rows per aggregate: 5; sum tolerance=max(2.0 lb, 1.0%).
  Multi-line/multi-ticket aggregates are expected for orders where several
  receipt rows add up to one DTC shipment/order weight.
  The number of tickets/lines in a valid aggregate does not lower confidence;
  aggregate confidence is based on material, summed weight, and date proximity.
  Greedy uniqueness is enforced in DTC row order: once an inbound row is
  assigned to a matched order, later orders must use other available rows.

RECOMMENDED THRESHOLD ADJUSTMENTS
  - Outbound High-confidence rows: 84/85. Agreement with ground
    truth is the key check above; if it is ~100%, current weights are sound.
  - Inbound scores top out lower (no customer/gross/location signal). If too many
    inbound rows land in 'Low', lower score_medium/score_min or raise w_net_weight
    and w_date for the inbound pass specifically.
  - Duplicate row-id notes mean the exact same source line was reused.
    Repeated ticket numbers alone may be valid multi-material tickets.
  - Tighten date_block_days if runtime grows on larger extracts; widen it if
    receipts can precede sales by more than two weeks in other yards.
